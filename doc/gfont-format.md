# 已验证的 .gfont 读写布局

[返回开发与验证](development.md)

本文记录解析器实际验证过的布局，便于维护读写兼容性；并不表示支持所有同扩展名文件。
字体的几何变形在解析后进行，不依赖文件名、作者或固定字符集合。

## 文件头与元数据

整数和坐标使用大端序。已验证的文件分为两类：

| 布局 | 文件头 | 字形 ZIP 条目名 |
|---|---|---|
| 明文元数据 | 版本 6，紧随 Java modified UTF-8 标记和元数据 | 字符本身 |
| 加密元数据 | 版本 5、6 或 7，紧随 uint32 密文长度和密文 | Unicode 码点的十进制字符串 |

当前明文布局通过已验证的 `xiongzai` 标记识别。加密布局中的来源标记按普通元数据处理，
不会要求输入字体具有某个特定名称或作者。

元数据包含来源标记、类型编号、字体名称、作者/标识、说明、坐标尺度和字数。
加密布局还包含两个附加字符串；已验证的版本 7 另有一个标识字符串。
字符串按 Java modified UTF-8 读写，支持 NUL 和 UTF-16 代理对。

元数据之后依次是 uint32 内置预览数量、对应的字形记录、完整字形 ZIP。
导出保留版本、加密方式、作者和附加字段，仅替换字体名称；内置预览与 ZIP 字形同步更新。
ZIP 条目名、顺序和注释也保留。

## 加密元数据封装

`glymorph/metadata.py` 使用标准库实现格式所需的 16 轮 TEA 和分组链接，固定键字节为：

```text
01 09 08 09 00 08 02 06 01 09 09 02 00 08 02 08
```

明文封装由长度标记、0～7 字节填充、两字节盐、元数据、七个零字节组成，
总长度为 8 的倍数。长度标记的低三位记录填充长度，高位保持实测文件中的 `0x20`。
设 `P` 为封装后的明文块，
`C` 为密文块，`E` / `D` 为 TEA 的分组加密 / 解密：

```text
X[i] = P[i] XOR C[i-1]
C[i] = E(X[i]) XOR X[i-1]

X[i] = D(C[i] XOR X[i-1])
P[i] = X[i] XOR C[i-1]
```

初始前块均为零。读取时检查分组长度与七字节零尾；写入使用由元数据哈希导出的确定性填充，
使相同生成参数的输出可以复现。这是字体格式的兼容性封装。
未改名时直接保留源文件头；改名时重新封装，不能在密文中直接替换字符串。

格式调查参考了 [CNCDraw 的读取器](https://github.com/jiangmuran/CNCDraw/blob/main/cncdraw/gfont/reader.py)
以及其 [TEA 格式说明](https://github.com/jiangmuran/CNCDraw/blob/main/cncdraw/gfont/tea_cipher.py)。
该项目被查阅的 Python 加解密入口未完整实现；Glymorph 的实现独立编写，
并通过用户提供的实际文件解密、元数据解析、改名和输出读回验证。

## 字形记录

普通字形包含：uint16 字符、uint32 坐标数、float32 坐标数组、uint32 指令数、指令字节。
每个点对应两个坐标和一个指令；`0` 表示落笔段起点，`1` 表示继续连线。

已验证的版本 7 还允许在同一字库内混用扩展记录：字符改用 modified UTF-8 字符串，
随后有四字节附加字段，再接普通记录中的坐标数、坐标和指令。
附加字段的业务含义尚未确认，因此逐字保留原始字节，不参与变形。
解析器只在版本 7 中尝试这一布局，并要求完整字节往返和 ZIP 名称匹配。

读取拒绝截断、未知尾随字段、重复字符、非法指令、非有限坐标、字数不一致和预览不一致。
输出不会丢弃无法识别的字形来换取成功。

## 验证边界

自动测试覆盖合成的加密版本 5/6/7 文件、扩展字形、元数据保留、加解密填充长度、
损坏文件拒绝和实际变形导出。用户字体集成测试使用 `tests/validate_fonts.py`。
这些检查验证文件与几何结果，不替代奎享客户端导入和物理写字机测试。
